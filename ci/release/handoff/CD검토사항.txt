SkinAI 실제 서비스 — CI 전달 기준

main 전환 준비 기준이다. 이 문서만으로 main 반영이나 Jenkins 설정 변경이 완료되지는 않는다.

정한 내용
1. Public 저장소: rlarns982/skinai-api, skinai-worker, skinai-patient-ui, skinai-doctor-ui.
   worker에는 실제 모델 3개를 포함한다.
2. API 18165, 환자 UI 18166, 의사 UI 18167을 사용한다.
   다른 PC 접속용 주소·방화벽·허용 설정은 CD에서 준비한다.
3. DB·사진은 새 버전을 배포해도 보존한다. 저장 위치와 백업 방법은 CD에서 준비한다.
4. main의 같은 커밋에서 UI·Backend·Workflow 모두 SUCCESS → 완성 이미지 연결 검사 →
   네 이미지 업로드·원격 확인 → release.json 전달 → CD 배포 순서다.
5. 사진 접수 → 분석 → 의사 확정 → 환자 결과 조회까지 확인한다.
6. 배포나 연결 검사 실패 시 이전 정상 이미지로 복구한다.
   DB·사진 백업·복구와 DB 구조 변경의 호환성은 별도로 정한다.

전달 파일
- candidate.json: 로컬 이미지 검사 자료이며 배포용 파일이 아니다.
- release.json: 공개 업로드·원격 확인을 마친 네 이미지의 고정 주소와 CI 근거.
  완성된 파일이 없으면 실패 또는 미완료이며 CD에 전달하지 않는다.
- 로컬 이미지 ID를 원격 digest로 그대로 복사하지 않는다.
- 메타데이터 검사 통과와 실제 배포 성공은 구분한다.

기존 CD 보존
- 기존 CD는 central/ai-mock, 18130 포트, skinai-cd-lab 전용이다.
- 새 api/worker/patient-ui/doctor-ui와 계약이 다르다.
- 기존 release.json, Jenkins 작업, Compose 프로젝트, .cd-state 복구 기록은 변경하지 않는다.
- 새 CD는 별도 프로젝트·저장소·복구 상태 경로를 사용한다.

CD에서 준비할 내용
- 네 서비스 Compose와 실제 접속 주소·접근 허용 설정.
- API/worker가 공유할 DB·사진 저장소와 백업·복구 절차.
- UI의 /api 연결과 모델 준비 상태 확인.
- 이전 정상 이미지와 데이터 구조의 호환성.
- 현재 의사 인증은 시연 토큰 방식이며 실제 서비스 인증은 별도로 적용한다.

현재 도구의 범위
- publish.py는 같은 PC의 명시한 세 Jenkins 빌드와 이미지 검사 근거를 읽는다.
- SkinAI-Release-CI에 네 이미지 업로드·원격 확인·release.json 보관이 구현되어 있다.
- 준비 코드의 기준은 main이다. 같은 main 커밋의 세 CI가 모두 SUCCESS여야 업로드한다.
- 전환은 ci/release/README.md의 순서로 진행하며 기존 CI 브랜치 성공 기록은 재사용하지 않는다.
- 새 전달 파일로 기존 CD를 자동 실행하지 않는다. 네 서비스의 CD 연결은 별도로 준비한다.
- 연결 검사는 모델의 의학적 정확도 평가를 대신하지 않는다.
