# 인증 검사 연결 준비

로그인 도입 전 `b0d15c3` 기준으로 기존 검사의 인증 처리를 공통 파일로 모은 보관용 준비 브랜치입니다. 이 브랜치의 동작은 **접수별 환자 토큰 + 시연용 의사 토큰**입니다.

2026-11-17 확인: 최신 main의 `3f7c2f2`에 실제 로그인 API와 UI가 추가됐습니다. 따라서 **이 준비본을 그대로 main에 합치지 않습니다.** 최신 로그인 코드를 기준으로 공통 도구를 다시 연결해야 합니다. `ci/ui_workflow/run_workflow.py`와 `tests/workflow`의 두 TypeScript 파일은 양쪽에서 변경됐습니다.

## 공통으로 수정할 파일

| 구분 | 파일 | 맡는 부분 |
| --- | --- | --- |
| Python 검사 | `ci/backend_contract/auth_support.py` | 접수 응답의 환자 토큰, 요청 인증 정보, 임시 의사 토큰 생성·읽기 |
| UI 검사 | `frontend/patient-frontend/tests/support/auth.ts` | 환자·의사 인증 정보, 인증된 API 요청 설정, 현재 의사 토큰 입력 화면 조작 |

사진 접수·모델 결과·의사 확정·환자 결과 공개 검사는 기존 파일에 남깁니다. Python과 UI 검사는 언어가 달라 각각 공통 파일 하나를 사용합니다. 실제 앱 코드와 Jenkinsfile, CD 코드는 바꾸지 않습니다.

임시 의사 토큰 두 개를 사용하는 기존 검사는 권한 분리를 확인하기 위한 것입니다. 실제 로그인 계정을 추가로 만드는 작업이 아닙니다. 공통 인증 도구는 오류 메시지에 토큰 값을 넣지 않습니다.

## 2026-11-17 전달받은 새 기준

| 항목 | 적용할 기준 |
| --- | --- |
| 환자 시작·내 예약 확인 | 이름 + 전화번호로 확인. 원래 브라우저의 접수 토큰이나 문자 인증을 요구하지 않음 |
| 의사 로그인 | 아이디 + 비밀번호가 맞아야 예약 목록 접근 가능 |
| 최소 준비 계정 | 의사 1개. 환자는 비밀번호 계정 대신 가상 이름·전화번호 한 쌍으로 검사 |
| 반복 실패 | 최신 main은 환자·의사 모두 5회 실패 시 5분 잠금. 다섯 번째 실패는 401, 이후 잠금 중 요청은 429 |
| 결과 공개 | 의사 확정 전에는 환자 응답·화면에서 결과 비공개, 확정 후 공개 |
| 범위 제외 | 이름·전화번호를 모두 아는 타인을 구분하는 본인 확인 기능·검사 |

현재의 접수 토큰 간 차단 검사는 기존 동작 유지 여부를 확인합니다. 새 이름·전화번호 조회 방식의 보안을 검증한 결과로 사용하지 않습니다.

## 최신 로그인 코드에 연결할 순서

1. 최신 main의 환자 조회 및 의사 로그인·로그아웃을 유지하면서 공통 인증 도구를 적용합니다. 이전 화면 조작 파일로 덮어쓰지 않습니다.
2. 이름·전화번호 일치/불일치, 의사 비밀번호 오류, 5회 실패 잠금 검사를 연결합니다. 환자 로그인 세션과 기존 접수별 토큰은 별도로 다룹니다.
3. 공통 인증 파일에 실제 API 연결을 추가하고, UI 공통 파일의 인증 화면 조작을 새 화면에 맞춥니다. 실패하면 기존 시연용 토큰으로 우회하지 않습니다.
4. 접수 시점과 환자 조회 절차가 달라지므로 기존 검사 흐름도 필요한 부분을 수정합니다. 공통 파일 하나만 바꾸면 전부 끝난다고 가정하지 않습니다.
5. 새 API로 다음을 실제 검사합니다: 환자 정보 일치/불일치 조회, 의사 정상 로그인/잘못된 비밀번호, 로그아웃 후 이전 인증 정보의 접근 차단, 환자 요청의 의사 기능 접근 차단, 5회 실패 잠금, 사진 접수부터 의사 확정 전후 결과 공개.

잠금 검사는 배포 중인 의사 계정이 아닌 **임시 검사 환경의 계정**에서 실행합니다. 이 준비 브랜치의 기존 검사 통과를 새 로그인 전체 검증으로 표시하거나, 건너뛴 테스트를 성공으로 취급하지 않습니다.

## 최신 main에서 확인한 내용

- 환자: `POST /api/auth/patient`의 `phone`, `name`, `create`로 시작/재조회. `GET /api/me/cases`는 로그인한 환자의 예약을 반환합니다.
- 의사: `POST /api/auth/login`의 `loginId`, `password`로 로그인. `POST /api/auth/logout`은 해당 로그인 세션을 삭제합니다.
- 별도 main 복사본에서 서버 검사 29개, 정책 검사 1개, HTTP 검사 20개를 실행해 통과했습니다. 임시 의사 계정으로 5회 실패 잠금·5분 후 해제·로그아웃 후 세션 차단도 확인했습니다.
- **기존 접수 토큰은 로그아웃 뒤에도 유효했습니다(조회 200).** 로그인 세션은 차단되지만, 모든 기존 접수 토큰까지 무효화되는 것은 아닙니다. 로그아웃 검사 범위를 맞춰야 합니다.
- CI 실행기는 임시 의사 계정을 준비합니다. 새 로그인 코드를 CD에 배포하려면 CD 환경의 `SKINAI_DOCTOR_ACCOUNTS`도 검사 계정과 맞아야 합니다. 실제 `runtime.env`와 비밀값은 열거나 수정하지 않았습니다.
- 새 로그인과 실제 3개 모델을 함께 실행하는 검사는 이번 main 확인에서 실행하지 않았습니다. 아래 기존 준비본의 UI 통과와 구분합니다.

## 준비본 확인 방법

프로젝트 최상위 폴더에서, 기존 백엔드 검사 패키지가 설치된 Python으로 실행합니다.

```powershell
python -B ci/backend_contract/test_auth_support.py
python -B ci/backend_contract/run_checks.py --source-root . --output-root verification/auth-prep/backend
```

UI의 공통 도구만 검사하려면 다음을 실행합니다. 실제 로그인 검사가 아니라 현재 토큰 처리와 잘못된 인증 정보 차단을 검증하는 테스트입니다.

```powershell
Set-Location frontend/patient-frontend
npm ci
npx playwright test --config playwright.auth-support.config.ts
```

전체 사진 접수·모델·의사 확정 UI 검사는 기존 `ci/ui_workflow/run_workflow.py`를 별도 임시 환경에서 사용합니다. 기존 실행기처럼 테스트 서버만 종료하며 배포 서버를 대상으로 실행하지 않습니다.

이 준비본은 `ci/auth-test-prep` 브랜치에만 저장합니다. main 병합이나 기존 Jenkins·CD 설정 변경은 포함하지 않습니다.

## 이번 확인의 범위

기존 접수 토큰 방식의 인증 처리와 의사 확정 전후 공개 검사를 유지하는 작업입니다. 이 브랜치 자체에는 새 이름·전화번호 조회, 아이디·비밀번호 로그인, 로그아웃, 5회 실패 잠금을 연결하지 않았습니다. 위 최신 main 검토는 별도 복사본에서 수행했습니다.

임시 통합검사 실행기의 worker 사진 폴더가 읽기 전용이어서 환부 표시 이미지(overlay) 저장 경고가 관찰됐습니다. 분석 결과와 의사 확정·공개 흐름은 통과하지만, 표시 이미지 저장 성공은 이번 UI 검사의 통과 범위에 포함하지 않습니다. 이 기존 검사 환경 설정은 인증 정리와 별도 사항으로 남겼으며 실제 배포 서버를 변경하지 않았습니다.
